# 当前页面上下文的显示策略（默认静默，仅受限页提示）

- 日期：2026-11-15
- 状态：已评审（三轮用户反馈：① 底栏徽章「已带上当前页面」不优雅，参考 Gemini 插件；
  ② 当前页应与「引用其它页面」同一套处理；③ 当前页的引用不需要显示）
- 取代：`2026-11-14-composer-page-context-badge-design.md` 的位置与内容两节；语义锚点
  （resolvePageAttached）、只画稳定态、无障碍挂法由本文档继承。
- 来源：当前页默认就进上下文（这是产品核心默认），给它画一枚常驻 chip——先是底栏徽章、
  再是 Gemini 式 chip、再是可 × 摘除的引用式 chip——无论哪种形态，都是在把"永远为真的事"
  每天在输入框上重复一遍。最终结论：可读页不显示任何东西；引用行只属于用户显式加进来的
  页面（@ 引用）。

## 1. 设计

- **默认静默**：可读的当前页不再有任何常驻指示。下一条消息带不带页面仍由
  `resolvePageAttached(pageContext.status)` 决定（`App.tsx` submitMessage），语义与
  2026-11-14 之前完全一致；`pageAttached` 挂/摘状态与 @ 选择器的「添加当前页面」入口
  已随本设计删除——没有显示就没有入口，留着即死代码。
- **受限页仍提示**：chrome:// 等读不了的页面画一枚灰色弱化 chip（favicon 或文档图标 +
  标题，tooltip 解释这类页面读不了），没有 ×。这是 2026-11-14 spec 补上的真正缺口
  （restricted 态无提示），保留；它不是"引用"，是"这轮为什么读不了页面"的答案，只在
  少数页面上出现，不构成噪音。`favIconUrl` 透传链路（`GET_ACTIVE_TAB` →
  `PageContextState`）为它保留。
- **@ 选择器**：当前页那一行是不可点的说明行（「当前页面 · 默认已包含」）。理由沿用：
  不列会让人疑惑"我这个页面为什么不在候选里"；列成候选又会被重复计进引用上限。
- **无障碍**：sr-only 状态文本只随受限页 chip 存在（「当前页面不可用」），仍经
  `aria-describedby` 挂在输入框上；可读页没有 chip，输入框没有 description，无副作用。

## 2. 非目标

- 不做任何"带上/不带当前页"的用户开关（曾实现过可摘除 chip，被「不需要显示」否决后无入口）；
- 不改 `resolvePageAttached` / `withoutBrowserTools` 的语义与刷新时机；
- @ 引用标签页的处理方式不受影响。
